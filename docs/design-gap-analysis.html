Confluence의 「벤치마크 프로세스 설계」와 「벤치마크 시스템 설계」를 현재 코드베이스와 비교하고, 실제로 수정해야 할 사항을 우선순위에 따라 정리한 문서입니다.

기준 코드: clio-benchmark 저장소 · 작성일: 2026-09-19

한눈에 보는 결론

전환 브랜치에서는 입력과 Ground Truth 분리, 결정적 평가, Case별 오류 격리, 결과 요약과 리포트까지 반영했습니다. “특정 Clio 버전을 직접 실행하고 정성 평가까지 완료하는 완전한 벤치마크 시스템”이 되려면 Runtime Manager와 LLM Judge가 추가로 필요합니다.

꼭 수정해야 하는 핵심 사항

1. 입력 데이터와 정답 데이터의 역할 분리

현재 benchmark.json은 사용자 Bug Report 역할을 합니다. 새 bugs.json은 실제 원인과 위치를 가진 정답입니다. 두 역할을 하나로 볼 수 없습니다.

  • cases.json: Clio에 제출할 사용자 관찰 정보
  • bugs.json: Evaluator만 읽는 Ground Truth
  • 두 파일은 동일한 case_id로 연결

2. Ground Truth가 Clio에 보이지 않도록 격리

bugs.json을 저장소에 추가하면서 기존 exclude 목록을 그대로 두면 Agent가 정답을 볼 수 있습니다.

  • Benchmark 전용 원본 workspace 유지
  • Case 실행 전에 Clio 전용 workspace 생성
  • 정답·평가 설정을 물리적으로 제거한 소스만 전달

3. 평가 가능한 내부 결과 모델 도입

현재는 Clio API 응답 형태에 직접 의존합니다. 평가 전에 결과를 안정된 내부 모델로 변환해야 합니다.

  • 판정, root cause, 파일 및 라인 범위
  • 근거, 해결 방법, confidence
  • 토큰, 도구 호출, 실행 시간

4. 실제 Evaluator 구현과 Runner 연결

현재 점수 합산 함수는 있지만 점수의 재료를 만드는 로직이 없습니다.

  • 먼저 파일·라인·탐지 여부를 결정적으로 평가
  • 의미 판단만 LLM Judge에 전달
  • 구조화된 평가 결과를 Score Aggregator로 전달

5. Case 단위 실패 격리

하나의 timeout이나 API 오류 때문에 전체 Run이 중단되지 않아야 합니다.

  • Case 루프 내부에서 오류 포착
  • CLIO_FAILED, INFRA_ERROR, TIMEOUT 기록
  • 남은 Case 실행 후 COMPLETED_WITH_ERRORS로 집계

6. Runtime Manager 추가

설정에 적힌 revision과 실제 실행 중인 Clio 코드가 일치하도록 Benchmark가 런타임을 소유해야 합니다.

  • clone/checkout/build/start/health/stop
  • Server·Agent 실제 commit SHA 기록
  • DB·Message Broker 등 의존 서비스 관리

먼저 확정해야 할 설계 결정

Bug 입력과 Ground Truth를 어떤 형식으로 관리할 것인가?

두 Confluence 문서에서는 bugs.json으로 Bug Report를 만든다고 설명하지만, 예시 데이터에는 사용자 입력에 필요한 재현 절차와 기대·실제 동작이 없습니다.

권장안: Clio 입력과 정답을 별도 파일로 분리합니다. 입력은 실제 사용자 Bug Report와 최대한 유사하게 유지하고, 정답은 Benchmark Evaluator만 접근하게 합니다. 이렇게 하면 데이터 누출을 예방하고 입력 시나리오도 독립적으로 개선할 수 있습니다.

권장 구현 순서

데이터 계약 확정

cases.json과 bugs.json 스키마, 연결 키, 버전 정책을 정합니다.

Workspace 및 정답 격리

원본 fixture와 Clio 노출용 workspace를 분리하고 누출 방지 테스트를 추가합니다.

결과 모델과 상태 모델 정리

NormalizedResult, Case 상태, 오류 유형, 상태 변경 시각을 정의합니다.

Deterministic Evaluator 구현

Bug 탐지, 파일·라인 위치, 누락, 실패, timeout부터 코드로 평가합니다.

결과 파일과 Summary 생성

input.json, clio-result.json, evaluation.json, metrics.json, summary.json으로 분리합니다.

부분 실패 지원

Case별 오류를 보존하면서 나머지 Case 실행을 이어가도록 Runner를 변경합니다.

Runtime Manager 구현

Clio 실행 환경을 자동화하고 실제 commit 및 환경 정보를 manifest에 기록합니다.

LLM Judge와 비교 리포트 추가

정성 평가, category별 결과, 이전 Run 대비 변화를 최종 단계에서 추가합니다.

현재 구현에서 유지할 좋은 기반

구조

단일 Python CLI, Runner 중심 오케스트레이션, API를 통한 Clio 호출은 새 설계 방향과 일치합니다.

재현성과 보안

suite commit 기록, secret redaction, 실행별 manifest와 원자적 파일 저장은 그대로 확장할 수 있습니다.

실행 흐름

프로젝트 생성, 저장소 등록, 동기화 대기, Bug 생성, 결과 polling은 핵심 수직 흐름으로 재사용할 수 있습니다.

평가 골격

품질 점수와 효율성 지표를 분리한 모델, 설정 가능한 가중치 구조는 유지할 가치가 있습니다.

주요 수정 대상 파일

suite.py
새 fixture 및 Ground Truth 데이터 모델
clio_client.py
정답 누출 방지와 workflow 추적 계약
runner.py
평가 연결, Case 오류 격리, 단계별 실행
evaluation.py
실제 deterministic/LLM 평가기
workspace.py
Clio 전용 workspace와 결과 파일 구조
manifest.py
세분화된 상태·환경·commit·모델 정보
cli.py
실제 setup/down/report 명령
config.py
Judge, runtime, dataset 설정 확장

검증 시 참고 사항

전환 후 테스트 fixture는 저장소 내부로 이동했으며 외부 디렉터리 의존성을 제거했습니다. 현재 단위·통합 테스트 17개와 Ruff 정적 검사가 모두 통과합니다.
